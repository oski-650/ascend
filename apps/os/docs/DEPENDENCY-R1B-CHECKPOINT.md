## 5 · The one mismatch: a PostgreSQL 17 → 18 catalog difference in F5

- **First verification:** every key matched except `F5.constraints.count` and
  `F5.constraints.digest`. Production (17.6) reported **43** constraints; the isolated restore (18.3)
  reported **85**.
- **Diagnosis** (local, against the artifact only; counts and constraint types, no row content):

  | Constraint type | c (check) | f (foreign key) | p (primary key) | u (unique) | n (NOT NULL, PG 18 only) |
  |---|---|---|---|---|---|
  | Count in the restore | 15 | 15 | 8 | 5 | 42 |

  - PostgreSQL 18 records each NOT NULL column property as a `pg_constraint` row of type `n`, and
    there are exactly 42 NOT NULL columns. PostgreSQL 17 does not record them.
  - Excluding type `n`: the count is **43, equal to production**, and the **digest of the 43 deparsed
    constraint definitions equals production's**.
- **Accepted normalization** (owner-approved):
  - Both F5 keys exclude `contype = 'n'`, so F5 represents cross-version-stable relational
    constraints.
  - **F2 stays the authority for nullability.** It digests `attnotnull` for every column on both
    versions, and it matched.
  - Production's stored F5 values were computed on 17, which has no `n` rows, so they are unchanged
    by the fix. No new production read was needed.
- **Regression proof** (`restore-fidelity.test.ts`, "R1b · F5 is cross-version-stable, and F2 keeps
  NOT NULL"), running on PostgreSQL 18 where type-`n` rows exist:
  1. F5 count = all constraints − type-`n` rows, and the type-`n` count equals the number of NOT NULL
     columns (so the test isn't vacuous).
  2. Dropping a NOT NULL changes F2 and leaves both F5 keys unchanged.
- **Mutation-verified.** Removing the exclusion from F5's count turns 2 tests red. Removing it from
  F5's digest turns 1 red. Removing `attnotnull` from F2 turns 1 red.
- **No other key changed, and F1–F18 were not otherwise altered.**

### The application consumes the restore

- The owner's restored credential accepts the real password (read in the emptied environment, never
  printed) and refuses a wrong one.
- The owner's principal resolves from the restored memberships.
- Under that principal the owner sees every restored prospect of the organization.
- **The application's own `readEvents` consumes the restored events** (added at conditional
  acceptance). The reader runs under the owner's real principal, with `requireCaller()` resolved from
  the restored memberships. It returns exactly as many events as the organization holds, as the
  application's mapped envelopes (a structured `subject`, ISO `occurred_at`). The set of event ids
  equals the restored table's, and the order equals the reader's contract (`occurred_at`, then `seq`).
  Separately, the restored `seq` order reproduces the production manifest's `F6.events.order.digest`.
  Only counts, digests and booleans are asserted, so no payload or event id can appear in output.
- **The reader proof is mutation-verified.** Each of these turns it red: removing the reader;
  bypassing it with raw SQL (caught by the envelope-shape check); reversing the reader's `seq`
  tie-break, which shows production has `occurred_at` ties and so the tie-break is really exercised;
  and the reader dropping one event. `core/db/events.ts` was restored byte-identical and is not part
  of this checkpoint.
- Behaviour checks hold for the organization: the next sequence value is beyond history, events
  refuse UPDATE and DELETE, RLS separates org and no-org and owner and sales, and only `ascend_auth`
  may read `password_hash`.

## 9 · Remaining limitations

- **R1c is required.** This proves a restore of production 17.6 state onto PostgreSQL **18.3**, not a
  same-version recovery. §5 is exactly the kind of difference a same-version restore would not have.
  PostgreSQL disaster recovery is not production-proven until a 17→17 `pg_restore` and a read-only
  application boot succeed.
- **R2 is required.** The vault has no proven recovery path and is not in this artifact.
- **Off-machine storage.** The artifact exists only on this Mac. B2 is selected but not configured,
  and upload, restricted credentials, versioning and Object Lock are separate bounded work.
- **Escrow.** The key's recovery copy is a locked Apple Note. Deployment secrets are not yet in
  escrow. An offline physical record is planned.
- **The August backups** are unchanged, awaiting the post-R1b decision.
- **Data sizes.** Production is small today; restore time scales with data. It was 4.2 s for 15 MB.
